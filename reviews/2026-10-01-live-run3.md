### What is accepted and what is refused

| input | result | proof |
|---|---|---|
| `bytes` | passed through, **no copy** | `_as_bytes(J) is J` → `True` (`read.py:942-943`) |
| `bytearray` | copied once to `bytes` | records equal the `bytes` records (`read.py:954-955`) |
| `memoryview`, `itemsize 1`, contiguous (incl. readonly over `bytes`) | copied once | records equal the `bytes` records |
| 2-D `cast("B", shape=[2,n])` | read as the run under it | `ndim 2, itemsize 1, c_contiguous True`; records equal |
| `memoryview.cast("H")` | `TypeError` naming `itemsize 2 with c_contiguous=True` | `read.py:944-953` |
| `[::2]`, `[::-1]` | `TypeError` naming `c_contiguous=False` | same branch |
| `str`, `int` | `TypeError` with the path rationale | `read.py:956-962` |

**The multi-dimensional case is right.** `itemsize == 1 and c_contiguous` is
exactly the predicate "names a run of bytes"; shape is metadata that cannot
change byte identity, and `bytes(view)` yields that run in C order on any
machine. Refusing it would reject input the library maps perfectly.

**The strided rationale does not hold as stated.**
`bytes(memoryview(bytearray(b"abcdef"))[::2])` → `b'ace'`, deterministically and
machine-independently: at `itemsize 1` no byte order is involved. So unlike the
wide-item refusal — which genuinely *is* `CLAUDE.md` invariant 4 — the strided
refusal is a **contract narrowing**, and "those bytes exist nowhere as a run in
your buffer" is a statement about intent, not ambiguity. It does **not** breach
invariant 2: a `TypeError` at the public boundary naming the fix
(`Pass bytes(view)`) is the loudest available outcome, not a silent discard, and
invariant 2 governs trace content rather than API typing. Narrow-now is also
the reversible direction. The choice is defensible; what is wrong is letting
the two refusals share one breath as though both were determinism.

### The multi-span thread — answered independently

**The loop shape is as described.** `api.py:182-189`: `_translate` once per
record, `begin()`, `for span in spans: self._absorber.absorb(span, producer)`,
then `_journal.record(...)`, `_version = position`, `_graph = None`. Each
`absorb` is atomic; the loop is not. The design contemplates multi-span —
`incremental.py:172-173` says "Open a journal entry: one arrival, however many
spans it became", and `api.py:336-358` `_numbered` iterates spans.

**No shipped adapter emits 2+ spans per record — confirmed by reading both,
not by taking the note's word.** `openinference.py:174-176` and
`otel_genai.py:268-270` are the same body —
`for index, record in enumerate(records, start=1): yield _parse_record(index, record)`
— and `_parse_record` returns exactly one `NormalizedSpan`
(`openinference.py:179`, `otel_genai.py:273`). Those two are the only
registered adapters (`adapters/__init__.py:324-325`); the unclaimed branch
returns a 1-tuple (`api.py:284`). Envelopes expand at the **reader**, not at
`feed`: `read_records` yields records and `feed` takes one, so a batch never
arrives as a single record. But the `Adapter` protocol states no cardinality
(`adapters/base.py:48-57`), `ADAPTERS.md` §2 says only "skip when there is
genuinely nothing to emit", and `spanweave.adapters.register` is public — so a
contributor's adapter reaches it. "Unreachable" is a property of the shipped
set, not of the contract.

**What a half-absorbed record actually leaves — demonstrated, not reasoned.**
With a registered stub yielding one record as two identical spans and the
second refused: `version == 0` while `graph()` returns **1 node** (a control
builder at version 0 returns 0). The next `feed` returns version 1 and
`graph()` has **2** nodes, not 1. And `delta(since=0)` reports only the later
node — so the half-arrived node is presented as **pre-existing in an empty
builder**. The cause is `Ledger.begin()` clearing the snapshot
(`delta.py:135-136`): the next `begin()` discards the pending additions and
`finish()` is never reached. So the state is **observably corrupt, and
silently** — a worse shape than the bug L10 fixed, which crashed loudly.

**Closing it is bounded:** a `rollback_to(n_spans)` that truncates
`_spans`/`_producers`, recomputes the three whole-input counts and
`_adapter_ids`/`_producer_latest` from the survivors, then
`_restate_every_record` — O(n), paid on refusals only, ~25 lines, nothing added

### Finding of this review: the atomic region stops short of `_translate`, and *that* is reachable with a shipped adapter

`Builder._translate` mutates **before** the loop: `self._claimed += 1`
(`api.py:273`, `289`), `sample.append(record)` (`api.py:287-288`),

three, so they survive a refusal — and `_claimed` is what gates `graph()`'s own
refusal (`api.py:261-262`). Probed with **openinference only**, no stub adapter:

```
A = {"foo": 1}                                   # unclaimed
B = {"span_id": derive(None, None, record_digest(A)),
     "attributes": {"openinference.span.kind": "LLM"}}

control (fed A only)       graph() -> AdapterSelectionError / adapter_unconfident
fed A, then B refused      DuplicateNodeIdError; version == 1; graph() -> built, 1 node
```

So §10.5's "every later `graph()` … answer[s] exactly as they would have had
the record never arrived" is **false with the shipped adapters**: the refused
record flipped `graph()` from refusing to building. The crafted `span_id` makes
it contrived, but trace payloads are untrusted input (`SECURITY.md`), and
`_unread` is cleared on the same path. `_sample` pollution is latent only —
both shipped `detect()`s return 0.9 on any marker
(`openinference.py:152-170`, `otel_genai.py:248-266`), so sample composition is
unobservable today; a third-party adapter with a proportional `detect()` would
expose it. The fix is the shape the commit already used: compute with a
prospective sample and commit the three counters after the loop.

### What the three prompted questions settled

1. **L10 / the multi-span loop (§5).** No shipped adapter yields 2+ spans per
   record — both registered adapters return exactly one `NormalizedSpan` per
   record, and envelopes expand at the *reader*, never at `feed`. But the
   `Adapter` protocol states no cardinality and `register` is public, so a
   contributor reaches it; and when reached the result is **silently corrupt**,
   not merely partial. More importantly the same promise is falsifiable **today,
   with openinference alone**, through `_translate`'s pre-loop mutations. →
   finding 1.
2. **L12 / where `undecodable_bytes` is emitted (§3).** Record-scoped from
   `_read_line` (before the parse), whole-input from `_read_array` (before) and
   `_read_document` (only after a successful parse, with the line-reader
   fallback reporting per line). When replacement makes a line unparseable you
   get **both** codes — never `malformed_record` alone — so the cause is never
   ambiguous. A receiver sees it identically through `read_records` and through
   a file read. The document-branch choice is right; the **array** branch is the
   coarse one. → thread 9.
3. **L14 / the 62 mid-stream windows (§7).** **Redundant by design**, verified
   in the code: `until` is hard-wired to `self._version`, and the tests reach
   `until < n` by calling `delta()` inside the feed loop — so a mid-stream
   window *is* a full-prefix delta of a shorter builder, bit for bit. 70
   mechanical plus 4 hand mutations found nothing selective; only a planted,
   state-keyed mutant is caught by the new windows alone. **Keep them** —
   coverage of 20 endpoint states the corpus never otherwise reaches, ~1 s of a
   24 s suite, honestly documented. The gap is not in the mutations; it is in
   the 5-record corpus. → F2/F4.
4. **`tests/serialized_shape.json` (§8).** Both regenerations are exactly what
   was claimed. The Graph half is byte-identical across `ce9ff17..9d7179a`
   **except L12's two documented vocabulary additions** — the precise answer,
   rather than yes or no — and L14's "all six identical" is true against the
   baseline it actually names (`be16fa8`), not against `ce9ff17`.
