## 1. Annotations can create undumpable graphs

`✓ Resolved` · High · 🐞 Bug · ≡ Correctness

**Description**

> `check_serializable()` delegates to `_stdlib_dump()`, whose `json.dumps` call leaves
> `allow_nan=True`, so `NaN` and positive or negative infinity pass annotation validation. These
> values can enter through `Graph.annotate()` or `annotate_many()` but are later rejected by
> `serialize._stdlib_canonical(..., allow_nan=False)`, which also affects both `dumps()` and `dump()`.

**Code** — `spanweave/annotate.py[R228-229]`

```diff
+def _stdlib_dump(value: JsonValue) -> str:
+    return json.dumps(value, sort_keys=True)
```

**Evidence**

> The annotation checker delegates to a permissive stdlib JSON encoder that accepts non-finite floats
> by default, while the canonical graph serializer explicitly sets `allow_nan=False` and translates
> the resulting failure into `GraphNotSerializableError`. This proves that the same value passes the
> public annotation boundary and fails only when the completed graph is exported.

Cited: `spanweave/annotate.py[118-149]`, `spanweave/annotate.py[228-229]`,
`spanweave/serialize.py[90-102]`, `spanweave/serialize.py[129-160]`,
`spanweave/serialize.py[129-153]`.

**Issue description**

> Annotation validation accepts non-finite floats even though graph serialization rejects them, allowing callers to construct a graph that cannot be dumped and breaking the annotation API's round-trip guarantee.

**Recommended Fix**

> Call `json.dumps` with `allow_nan=False` in the annotation validation helper so it uses the same strict JSON policy as graph serialization. Ensure `NaN`, positive infinity, and negative infinity raise `ValueError` during `annotate` and `annotate_many` rather than later during `dumps` or `dump`, and add tests for each non-finite value at both top-level and nested positions.

## 3. Unclaimed nodes lose exact source bytes

Medium · 📘 Rule violation · ≡ Correctness — **declined**

**Description**

> `unclaimed_span` puts the already-parsed `record` object into `RawRecord.source`, rather than the
> exact bytes or line text received by the reader. Inputs that differ only in whitespace, key order,
> escape spelling, or numeric rendering therefore create nodes with indistinguishable source payloads.

**Code** — `spanweave/seam.py[359]`

```diff
+        raw=RawRecord(source=record, line_number=line_number),
```

**Evidence**

> Rule 2817492 requires every node factory to retain the exact inbound source without parsing or
> reserialization. The reader parses the line into a JSON value before the new `unclaimed_span`
> factory assigns that parsed object to `RawRecord.source`.

Cited: Rule 2817492, *Preserve original source payload on each node*;
`spanweave/read.py[284-298]`, `spanweave/seam.py[355-370]`.

**Issue description**

> `unclaimed_span` stores a parsed JSON value as the raw source, which cannot preserve the exact input encoding and spelling required for each node.

**Recommended Fix**

> Carry each record's exact input bytes or text through the read and dispatch pipeline, store that value in a dedicated raw-source field on `RawRecord`, and keep the parsed JSON value separately for mapping.

## 8. Long integer keys become unwritable

`✓ Resolved` · Medium · 🐞 Bug · ≡ Correctness

**Description**

> `_swap_long_integers` applies replacement only to mapping values and copies integer keys
> unchanged, allowing those keys to reach the standard-library encoder under a caller-controlled digit
> limit. When that limit is below a key's length, both the initial and retry dumps raise `ValueError`,
> so accepted annotation values and canonical graph serialization behave differently across
> interpreter settings.

**Code** — `spanweave/jsoncodec.py[R241-243]`

```diff
+        if isinstance(original, Mapping):
+            for key, item in original.items():
+                copy[key] = replacement(item)
```

**Evidence**

> The codec retries serialization after replacing long integers, but its mapping-copy loop passes
> original keys directly into the copied dictionary and applies `replacement()` only to values. The
> module documentation identifies the interpreter limit as process-dependent, while annotation
> validation accepts this shape without traversing keys on the assumption that encoding them as
> strings is safe, and canonical graph serialization then routes the data through the incomplete
> codec.

Cited: `spanweave/jsoncodec.py[3-21]`, `spanweave/jsoncodec.py[148-179]`,
`spanweave/jsoncodec.py[216-245]`, `spanweave/annotate.py[157-176]`,
`spanweave/jsoncodec.py[216-246]`, `spanweave/serialize.py[105-161]`.

**Issue description**

> The deterministic, interpreter-independent integer encoder replaces long integer mapping values but leaves long integer keys for `json.dumps` to stringify. Under a lowered interpreter digit limit, serialization can therefore reject an annotation value that validation accepted and make graph output dependent on interpreter settings.

**Recommended Fix**

> Handle supported integer mapping keys during the codec fallback as well as values. Extend the placeholder mechanism to convert keys through `integer_text` using key-specific quoted replacements so the resulting JSON exactly matches normal `json.dumps` key encoding; alternatively, reject non-string keys consistently during annotation validation so no long integer key reaches interpreter-dependent conversion. Add tests under a lowered integer digit limit, including nested mappings and keys near the library limit.

## 9. Mixed inputs get false attribution

`✓ Resolved` · Medium · 🐞 Bug · ≡ Correctness

**Description**

> `_sole_contributor` excludes `None` producers before deciding whether one adapter produced the
> entire input. When named-adapter spans coexist with unclaimed spans, graph-wide diagnostics such as
> `missing_trace_id` incorrectly name that adapter.

**Code** — `spanweave/build.py[R243-246]`

```diff
+def _sole_contributor(producers: Sequence[AdapterInfo | None]) -> str | None:
+    """The one adapter that produced every node here, or `None`."""
+    named = {producer.id for producer in producers if producer is not None}
+    return next(iter(named)) if len(named) == 1 else None
```

**Evidence**

> Automatic classification explicitly appends an `adapter=None` contribution for unclaimed records.
> The new helper filters that value out and its result is then attached to whole-input diagnostics,
> contradicting its own documented requirement that one adapter produced every node.

Cited: `spanweave/api.py[97-105]`, `spanweave/build.py[174-193]`,
`spanweave/build.py[243-246]`, `spanweave/build.py[383-407]`.

**Issue description**

> Mixed named and unclaimed contributions are incorrectly treated as having one sole adapter, causing graph-wide diagnostics to carry false provenance.

**Recommended Fix**

> Return an adapter ID only when the producer sequence is non-empty and every producer is non-null with the same ID; otherwise return `None`. Add coverage for a graph containing both a claimed record and an unclaimed record.
