## 2. Cross-cutting findings

### F1 — [blocker for R7 / series close] R6's correction is false on CPython 3.14, which is what `uv run` picks in this repo **[verified here]**

`SPEC.md` §7 now states, in bold, *"the encoder's limit **is** the parser's"*, and
the CHANGELOG states the mechanism as *"both draw on one interpreter-wide C
recursion budget"*. Both are universals. I bisected `json.loads` and `json.dumps`
(under this library's canonical `dumps` arguments) for **lists** and for **dicts**,
in fresh processes:

| Python | loads dict | dumps dict | direction |
|---|---|---|---|
| 3.11.15 | 992 | 992 | coincide |
| 3.12.3 | 9997 | 9997 | coincide |
| 3.13.14 | 9998 | 9998 | coincide |
| **3.14.6** | **40106** | **37241** | **encoder gives out first** |

A spanweave graph document is nested **dicts** at every level
(`nodes` → node → `raw` → `source` → `attributes`). So on CPython 3.14 the encoder
gives out ~2,865 levels *before* the parser, for exactly the shape the document
has — which is A6's original claim, the one R6 went out of its way to retract.
The SPEC's closing sentence, *"On an interpreter whose encoder has headroom over
its parser the four levels cost nothing and no trace file reaches the refusal at
all"*, is falsified end-to-end on 3.14: the R6 sub-agent measured a readable
ceiling of 37257 against a writable ceiling of 37241 — a 16-level
readable-but-unwritable band, not zero.

**Why nothing caught it.** Two independent reasons, and both need fixing:

1. `tests/test_serialize.py::test_the_encoder_does_not_give_out_before_the_parser_does`
   bisects honestly — no hard-coded constant, only a `CALL_PATH_SLACK = 16`
   tolerance — but `_nest(depth)` builds **lists**. Re-run verbatim with
   `{"a": ...}` on 3.14 it fails: `the parser reads 40071 levels and the encoder
   writes 37209`, against a 16-level slack. The test is green by accident of
   container shape, which is precisely `CONTRIBUTING.md`'s bar item — *"no test
   whose result depends on what happens to be installed on the machine running
   it"* — in its purest form: it passes in every environment where it cannot
   catch anything.
2. `.github/workflows/ci.yml` runs a matrix of `["3.11", "3.12", "3.13"]` while
   `pyproject.toml` declares `requires-python = ">=3.11"`. Every version CI tests
   coincides; the only version that diverges is the one CI does not test and that
   a local `uv run` selects by default. The blind spot is structural, not bad luck.

**Fix.** (a) Demote the SPEC heading and the CHANGELOG mechanism sentence from
universals to an observation naming its interpreter — the *positional* claim (four
levels, `nodes`/node/`raw`/`source`/`attributes`) is R6's real contribution, it is
correct on both interpreters I measured, and it is soundly pinned by the second
test. (b) Delete "no trace file reaches the refusal at all". (c) Make the limit
pin measure dicts, and have it record the observed ratio rather than assert a
direction the library does not control. (d) Add 3.14 to the CI matrix, or state
an upper bound in `requires-python`.

Note the shape of this defect for the series' own record: R6 is the *second*
consecutive attempt to state this fact and the second to over-claim. A6 said
"encoder lower" from one measurement; the run-2 review said "~1.9× higher" from
one measurement; R6 said "identical" from one measurement. All three measured one
interpreter and wrote a universal, and R6 additionally measured the wrong
container. The lesson that belongs in `DEBT.md` or `DECISIONS.md` is that this
quantity is not a fact about the library at all.

### F2 — [should-fix] `spanweave build` is not deterministic across machines for R1's inputs **[verified here]**

PYTHONINTMAXSTRDIGITS=0        4e0699a42c6df0f1f6a4ceecaa7d5d5d

## 3. R1 — `0e4262e` timestamps: finite and within the interpreter's reach

**§0.2: PASS on every item.** SPEC §3.1/§3.7/§7/§3.10 move in the same commit;
24 of 31 new test ids fail on the parent worktree as genuine assertions (e.g.
`ValueError: Exceeds the limit (4300 digits)` out of
`openinference.py:631`, and `assert inf is None`); the 7 that pass are the
declared pins; `serialized_shape.json` untouched and correctly so; `make check`
green (2229/2).

Both defects reproduce on the parent and are gone at the commit: `spanweave build`
on a quoted 5000-digit timestamp printed a **traceback**; a bare `NaN` was written
into stdout as `"started_at":NaN`.

**Q1 — is refusal right, is there a lossless degradation, is it routable?**

*(a) Right.* Yes, and it is the only option that does not lie. `raw.source` is
verbatim by contract (§3.5); the value in the record genuinely is a Python `inf`;
RFC 8259 has no token for it. The parent's behaviour — writing bare `Infinity` —
is the worst outcome available: the file looks written and no strict parser can
read it back. Coercing to `null`/`0` would be a silent drop (invariant 2). The
honest counter-argument, which SPEC does not state: this is the harshest
degradation in the codebase (one `NaN` anywhere destroys a 100k-span graph),
everywhere else "degrade honestly" means *diagnostic plus degraded graph*, and the
triggering data is not the user's to fix.

*(b) A lossless degradation exists, and it is a spec conversation, not a patch.*
Instrumented walk of `to_document()` over three traces: **`raw.source` is the only
field a non-finite value survives into** —
`.nodes[0].raw.source.start_time`, `.nodes[0].raw.source.attributes.*`. `usage`
stayed `None`; `started_at`/`ended_at` are the only float-typed model fields
(`model.py:206-207`) and R1's rule already covers them. So SPEC §7's claim is
accurate. The value enters at **`read.py:280` — `yield json.loads(line)`** (also
`:210`, `:243`), which passes neither `parse_constant=` nor `parse_float=`, and
reaches the encoder at **`serialize.py:160` — `"source": node.raw.source`**. A
JSON-legal, literal-preserving degradation is two hooks: `parse_constant` for the
bare `NaN`/`Infinity` tokens, `parse_float` for `1e400` (which is not a
"constant"). **Notably the library already does this elsewhere**: an
`input.value` of `{"x": NaN}` is emitted as the *string* `'{"x": NaN}'`. So the
codebase is not internally consistent about whether a non-JSON literal may be
carried as text — worth a §3.5 sentence either way.

*(c) Routability.* See **F4**. Exit codes observed: `build` on `NaN` → exit 1,
one stderr line, no traceback; `inspect` → exit 0 with a full summary; the library
raises `GraphNotSerializableError` with `.code == "graph_not_serializable"`, so it
is distinguishable from Python and not from the CLI. `python -m spanweave` does
not exist (no `__main__.py`).

**Q2 — digit-limit containment. Contained on all nine path × input combinations,
zero tracebacks, exit codes 0 or 1 only.**

| path | input | exit | result |
|---|---|---|---|
| `spanweave.build()` | bare, 1 record | — | raises `AdapterSelectionError` (`adapter_unconfident`) |
| `spanweave.build()` | bare + valid span | — | graph, 1 node, `malformed_record` |
| `spanweave.build()` | quoted | — | graph, `started_at=None`, `missing_timestamp`+`unmapped_attributes` |
| `spanweave build` | bare, 1 record | 1 | `no adapter is confident enough…` |
| `spanweave build` | bare + valid | 0 | graph, 1 node |
| `spanweave build` | quoted | 0 | 5000 nines round-trip verbatim, `"started_at":null` |
| `spanweave inspect` | bare, 1 record | 1 | `no adapter is confident enough…` |
| `spanweave inspect` | bare + valid | 0 | `nodes: 1`, `malformed_record: 1` |
| `spanweave inspect` | quoted | 0 | `nodes: 1`, `missing_timestamp: 1` |

One untested path: a trace whose **only** record is the bare literal exits 1 via
`adapter_unconfident`, not 0 with `malformed_record`. Every shipped test adds a
second valid span, so that shape is uncovered.

**Other findings.** [should-fix] `errors.py:107-119`'s `GraphNotSerializableError`
docstring still says `json.dumps` answers depth with `RecursionError` — *"not a
`ValueError`"* — and this commit adds exactly a `ValueError` arm; `errors.py:46-50`
still says only "nests deeper". SPEC §3.10 was updated, the code's own docs were
not. [nit] `except ValueError` at `serialize.py:77` is broader than its message —
`json.dumps` also raises `ValueError("Circular reference detected")`, which would
be reported as "it holds a number JSON has no way to write". [nit] Zero conformance
fixtures added; every case is inline in `tests/`. A refusal has no canonical graph
to express, so this is defensible, but the Definition-of-Done checkbox is unmet
and nothing says why. [nit]
`test_nothing_this_library_writes_can_contain_infinity_or_nan` names a
whole-library property and tests three float constants, with its post-write
assertion marked `# pragma: no cover`.
