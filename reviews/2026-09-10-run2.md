## 2. Findings

### 2.1 blocker — C3 reintroduces an uncaught exception on untrusted input

`spanweave/adapters/openinference.py:637` and `otel_genai.py:791` (identical line):

```python
return int(value) if _JSON_INTEGER.fullmatch(value) else float(value)
```

C3 made `_as_time` honour a *quoted* integer literal. `_JSON_NUMBER` matches a
numeric string of any length, so a `start_time` string of >4300 digits — legal
JSON, and exactly the untrusted input `SECURITY.md` describes — reaches
`int(value)` and raises CPython's integer-string-conversion `ValueError`, which
escapes `spanweave.build`.

Reproduced by me at **HEAD (`fcc842d`)**, not only at `c2486ba`:

```
$ spanweave build big.jsonl     # 4401-digit quoted start_time
  return int(value) if _JSON_INTEGER.fullmatch(value) else float(value)
ValueError: Exceeds the limit (4300 digits) for integer string conversion:
            value has 4401 digits; ...
exit=1
$ spanweave inspect big.jsonl   # same traceback
```

`validate` is unaffected (it reads graph documents, not traces).

It is a **regression from C3**: on `03ab6ee` (C3's parent) the same input builds
and yields `Infinity`. Wrong, but not a crash.

Why it matters beyond the traceback: this is precisely the class A6 spent a whole
batch closing one commit earlier — deep/hostile input must become a diagnostic,
never an escape. `CLAUDE.md` invariant 2 says input the library cannot map becomes
a diagnostic and *"'it vanished' is a bug"*; `SPEC.md` §7 says a failing command
prints one line. The bare-integer form of the same value is already handled and
produces a typed `AdapterSelectionError`; only the quoted path crashes.

The fix is one line in each adapter and belongs in a batch, not in this review.

### (2) A6 — `GraphNotSerializableError`

**Spec and table: yes, and the gate is real.** `SPEC.md:616` carries the
`graph_not_serializable` row; `spanweave/errors.py:49` defines it and lists it in
`ERROR_CODES`; `spanweave/__init__.py` exports it. `tests/test_codes.py:42`
asserts *set equality* between §3.10's codes and `ERROR_CODES` — deleting the SPEC
row fails it with "Extra items in the right set", so it catches drift in both
directions.

**No partial graph file can be written — structurally.** There are exactly two
write paths in the library: `serialize.py:101` `path.write_bytes(dumps(graph))`
and `cli.py:199` `sys.stdout.buffer.write(serialize.dumps(graph))`. Both fully
materialize the bytes in memory first (`canonical_bytes` is a single
`json.dumps` to a `str`), and the raise happens inside that call, before any
write is entered. The path is never opened, so it is never created or truncated.
Confirmed empirically: dumping to a new path leaves no file; dumping over an
existing file leaves its bytes byte-identical; `build -o out` returns 1, prints
one line on stderr, and `out` does not exist; `build` to stdout returns 1 with
exactly `b""` on stdout.

**Two caveats.** First, `tests/test_codes.py:51`
`test_every_error_type_carries_a_registered_code` enumerates error types by hand
and was *not* extended with the new one. Second — and this is a should-fix on the
commit's honesty rather than its code — the failure it guards is **not
reproducible on CPython**. The body and `CHANGELOG.md:18` claim the encoder's
limit is lower than the parser's ("the encoder meets a value four levels further
down"); measured on this interpreter, `json.loads` gives out at depth 40112 and
`json.dumps` at 74493 — the four levels cost 7, not 34,000. A sweep over every
depth from limit−60 to the limit exits 0 and writes the graph. The guard is
correct and cheap; the defect it narrates is presented as one users hit.

### (3) F2 — `timestamp_unit_suspect` on OTLP

**(a) It is structural, and it fires on every conformant OTLP file — but not on
the committed fixtures.** OTLP declares `startTimeUnixNano` in nanoseconds, so
every conformant value exceeds the `100_000_000_000` ceiling. Measured on
hand-made envelopes: N spans → N warnings, uncapped, one `warning` per node.

The two committed fixtures **do not fire it** — I checked before the reviewer
reported the same thing. `fixtures/conformance/otlp_container/dialects/*.json`
carry `startTimeUnixNano: "1000.0"`, `"1000.2"` … (`llm_tool_llm`'s *seconds*),
and both build with only `unmapped_attributes ×2`. That choice is disclosed in
`scenario.md`'s "## Timestamps" section and is what makes the byte-identical-graph
claim possible — but it means the corpus contains no realistic OTLP timestamp and
the 100%-warning behaviour ships untested.

**(b) The consequence is signal inversion, and I measured it.** On a 201-span
file — 200 nanosecond spans plus one genuinely seconds-encoded span:

```
total diagnostics: {'timestamp_unit_suspect': 200}
nodes: 201   warned: 200
the seconds-encoded span warned?: False
```

The entire diagnostic channel is consumed by 200 identical warnings, and the one
span that actually differs in unit is the only one *without* one. `SPEC.md:200`
says the per-node design exists to express exactly the "one exporter in seconds,
another in nanoseconds" case; on an OTLP export that case is now signalled by
absence among noise rather than by presence.

**(c) The reader could state the unit — and this is the first commit where that
becomes true.** `startTimeUnixNano` declares its unit *in the field name*. That
is the telemetry saying so, not a computation — the `explicit` side of the line
invariant 3 draws for edges. `read.py` already discriminates on precisely this
basis one level down ("where the format states a type, the reader honours it" —
so `{"intValue": "42"}` is decoded and `startTimeUnixNano` is not); the unit is
the same kind of fact one level up. `SPEC.md` §3.1 already says in prose that the
field "is what OTLP JSON's `startTimeUnixNano` is".

What it would cost: the record shape alone cannot carry it (a reserved record key
would make the reader speak past the seam), so it needs a `NormalizedSpan` field —
`started_at_unit: str | None` — plus a builder rule that suppresses or supersedes
the suspicion when the unit is declared. Additive at the seam; touches no
`NodeKind` or `EdgeKind`, so not a closed-enum halt; it does touch a frozen model
type and `SPEC.md` §3.1, so under invariant 6 it is a **spec conversation**. It
would move `serialized_shape.json` only if the unit is surfaced on `Node`. A
zero-model-change half-measure also exists: have the diagnostic name the source
field, or add a reader-side `info` code, so the pair is at least honest.

**Recorded as a follow-up for the maintainer, not as a defect of `ff05b2d`.**

**(d) One small honesty gap that *is* this commit's.** The words "suspect" and
"1e11" appear nowhere in the text `ff05b2d` adds — not in `SPEC.md` §7, the
CHANGELOG entry, `scenario.md`, the notes files or `ADAPTERS.md`. §7's timestamp
sub-bullet stops at "carried verbatim and read by §3.1's rule". A reader learns
that OTLP JSON is supported and does not learn that every file of it produces one
warning per span. One sentence would close it.

## 8. Method

`uv run --extra dev pytest`. New tests were copied into the parent tree with their
fixtures, and each reviewer distinguished a genuine assertion failure from an
import or fixture error. `git stash` and `git checkout <parent> -- spanweave` were
not used.
